# Z3

## What it is

Z3 is a satisfiability modulo theories (SMT) engine: it solves logical formulas together with typed arithmetic and other theories. Here a **theory** supplies the rules for a sort, such as mathematical integers or fixed-width bit-vectors. A bit-vector is an integer-like value whose arithmetic wraps at its declared width.

## Routes and classes

All three routes belong to `:solve-z3`, artifact `kt-constraints-solve-z3`.

| Route | Kotlin API | Binding |
|---|---|---|
| `z3/direct` | `Z3Backend` | Bundled Z3 Java API |
| `z3/wasm` | `Z3JsBackend.load()` | Asynchronously initialized `z3-solver` Wasm module |
| `z3/native` | `Z3NativeBackend` | Dynamically loaded Z3 C API |

The routes share [support inspection](https://github.com/gciatto/kt-constraints/blob/develop/solve-z3/src/commonMain/kotlin/io/github/gciatto/ktconstraints/solve/z3/translation/Z3Support.kt) and session logic; each uses a platform binding. Each is included in its platform's automatic defaults.

## Platforms and runtime requirements

The Java binding runs on the JVM. The JS binding runs on Node and in browsers; browsers require cross-origin isolation and the runtime assets. Close the loaded JS backend to terminate its workers after closing its solvers. Native uses `KT_CONSTRAINTS_Z3_LIBRARY` or the platform loader path; one Z3 library is loaded per process, and changing paths after loading is rejected.

See [platform availability](../../reference/platform-availability.md) for tested operating systems and Chromium coverage, and [configuration](../../reference/configuration.md) for library names. Native build targets do not by themselves provision a Z3 runtime, including on iOS.

## Capabilities

All routes offer batch satisfaction, integer optimization and projected satisfaction enumeration. Finite output domains permit exhaustive enumeration; real-valued outputs may instead produce an endless stream of distinct rational witnesses, since blocking individual values cannot exhaust a real interval. They also create incremental solvers with assertion checkpoints, backtracking, temporary assumptions and unsatisfiable assumption cores. An assumption is a formula applied to one check; a core identifies assumptions sufficient to make that check inconsistent.

`SatisfiabilityStore` can wrap these incremental solvers. It answers entailment by additional satisfiability checks; it does not expose native domain narrowing. Entailment asks whether current assertions force a formula to hold. See [solving modes](../solving-modes.md) and the [route capability reference](../../reference/solvers-and-routes.md).

## Supported modelling features and numeric limits

The adapter accepts Boolean formulas, finite-domain arbitrary-precision integer arithmetic (including products), exact rational linear real arithmetic, integer-to-real conversion, and the model's bit-vector operations. A rational is an exact fraction. Linear real arithmetic allows sums and multiplication by rational constants, rather than multiplication of real variables.

There is no fixed adapter magnitude bound on integers. That does not make integer domains infinite: the current integer variable API uses finite domains. Integer objectives are optimized by repeated bounded checks. Real objectives, and therefore linear and mixed-integer programs, go to Z3's optimizer, with its Farkas-based engine. Its answers are claims, not proofs: Z3's mixed-integer optimization can report wrong bounds, so an attained optimum `v` is reported only after the plain solver finds nothing better than `v`, and an unattained bound `u` only after it finds nothing reaching `u`. A refuting model becomes the incumbent and the optimizer runs again above it; claims still unconfirmed after a few rounds leave a `FEASIBLE` incumbent without a bound. Unboundedness is taken from the optimizer. Theories outside the modelling language are unavailable.

Globals use exact translations: all-different becomes Z3 distinct, tables become disjunctions of tuples, element and min/max use conditional expressions, and structural globals use their decompositions. Unsupported expression classes are reported explicitly. Shared capability names do not imply support for arbitrary custom expression implementations. Returned full assignments are checked before projection; see [architecture](../architecture.md).

## Options type

There is no Z3-specific `BackendOptions` implementation. Use `SolveOptions` for timeout and solution limits. `Z3NativeBackend` also takes a library path. See [configuration](../../reference/configuration.md).

## Performance

The recorded route catalogue shows substantial costs for Z3 on larger all-different problems and pigeonhole contradictions, compared with CP routes. Wasm has a noticeable fixed cost on small Node models; Native and JVM are measured separately. The catalogue's bit-vector example is small and it has no real-arithmetic family, so those measurements cannot establish a general SMT performance rule. See [benchmarks](../../reference/benchmarks.md) for numbers and conditions.
